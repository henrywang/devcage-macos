Communication Style

## Response Style
- Be concise, no trailing summaries of what you just did
- Prefer clear naming and simple structure over code comments
- Add comments only to explain why: non-obvious business rules, workarounds, external constraints, security decisions, or surprising edge cases
- Don't add comments that restate what the code does or narrate it line by line
- Don't use emojis
- When showing file edits, explain why, not just what

---
Coding Preferences

## Code Style
- Prefer explicit over clever
- No unnecessary abstractions for one-off use
- Don't add error handling for impossible scenarios
- Don't silently swallow errors; log or propagate them
- No docstrings unless I ask
- Prefer early returns over nested if-blocks

## Security
- Never commit secrets, credentials, API keys, tokens, or certificates
- Never disable or weaken TLS verification, authentication, or authorization, even in test code

## Testing
- Write tests for new functionality, using the test framework the project already uses
- When iterating on a fix, run the single relevant test or test file, not the whole suite

Workflow

## Git
- Always write commit messages in imperative mood ("Add X", not "Added X")
- Use conventional commits: feat/fix/chore/docs
- Use only a subject line for small or simple changes
- For complex or non-obvious changes, add a short body explaining why, risks, or important behavior; don't list changed files
- Do not include Co-Authored-By in commit messages

## Before finishing a task
- Run lint, typecheck, and tests if the project has them
- Check for obvious security issues: hardcoded secrets, SQL injection, XSS, unsafe shell interpolation

## Documentation
- Update existing docs when a change affects configuration, public APIs, or behavior
- Don't document features that don't exist yet

## Agent skills
- A third-party skill is any skill, plugin, or instructions bundle I didn't write. These rules also cover MCP servers and plugins, including ones bundled with a skill
- Before installing or updating one, download it at an exact commit or version into an empty temporary folder. Never install from a moving branch or tag, and never enable auto-update
- Review it there, not inside a skills folder: read SKILL.md and every script. Never run its scripts, installers, or hooks during review
- Scan it with `skillspector scan <folder> --no-llm`. Updates get a full rescan, not only a diff review
- Don't enable skillspector's LLM analysis unless I ask; it sends the skill to a model provider
- If skillspector is unavailable, stop and tell me; don't skip the scan or install it silently
- Act on the verdict: REJECT means don't install; CAUTION means show me the findings and wait for my approval; APPROVE may proceed. Never override HIGH or CRITICAL findings because of the publisher's reputation
- Show me the verdict, score, and source commit before installing
- Install a skill by copying the scanned files into `~/devcage-macos/config/.claude/skills/<name>/` (linked into `~/.claude/skills` by setup.sh), not with `npx skills add` or other installers
- Prose meant to be published or read by others (blog posts, articles, social posts, README and docs prose):
  - When you draft or rewrite it, check your draft with /no-ai-slop before showing it to me, and fix what it finds
  - When it's my own writing, run /no-ai-slop in detect mode only and list the findings; don't rewrite it unless I ask
- Don't run /no-ai-slop on chat replies, commit messages, code comments or code
